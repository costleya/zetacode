# Production parity evidence

`test/parity/corpus.json` is original synthetic data. Freeze it and record its SHA-256 before collecting paired results. The harness does not run models or manage servers. A build-specific adapter must use that build's actual completion path, including production prompt construction, gRPC, parsing, applicability and edit application. An installed-extension run requires extension-host instrumentation: source-level calls alone do not establish installed or editor-visible parity.

Run `node tools/parity/run.mjs --adapter /absolute/path/to/adapter --out /absolute/path/to/evidence.json --build BUILD_ID --environment /absolute/path/to/environment.json`. Repeat on each build under identical hardware, editor/profile, model weights, runtime and cache controls. Invoke the adapters only after the runtime owner authorizes and serializes GPU use. The command launches one adapter process per sequence; the adapter must prepare a genuinely cold process/model for `cold` or report that the condition was not achieved. Warm means the adapter has completed model warmup before its first measured step. Cache state must be reported, not inferred from sequence labels. Do not compare cold runs unless actual lifecycle evidence supports them.

Adapters communicate JSON lines over stdin/stdout. On start the harness sends `{type:"sequence", sequence, cases}`. The adapter sends exactly one `{type:"result", step, ...}` per step in order, then `{type:"done", conditionEvidence}`; diagnostics belong on stderr. Each result must include `prompt` (exact string), `generated` (complete model output), `finishReason`, `edit` (null or `{start,end,text}` with UTF-16 offsets), `appliedText` (null if no applicable edit), `firstUsableMs` (number or null), `completeMs` (number), `grpcMs` (number), `classification` (one of `usable`, `no-edit`, `incorrect`, `cancelled`, `error`), and `events` (ordered observable presentation/cancellation events). Time measurements start at request initiation; `firstUsableMs` must measure actual usable presentation, not first token. `incorrect` requires a reviewer note in `review`; model quality labels must be reviewed independently against the fixture intent, not inferred from text equality. Each result includes `cacheEvidence` explaining actual prompt and model cache state, and `pathEvidence` identifying build, production code path and transport. Failed, missing or ambiguous evidence invalidates the run rather than silently passing. Output contains full prompts and outputs (synthetic input only), hashes, edits, and timing; keep files outside the repository if runtime metadata is sensitive.

Compare with `node tools/parity/compare.mjs baseline.json rebuild.json`. Exact prompt and generated hashes are reported separately from applied-text/edit parity; floating-point generation differences require semantic review, not automatic equivalence. Compare first usable and complete latency separately, grouped by sequence/step. This harness does not itself prove editor UX, cancellation race correctness, managed-server lifecycle, or package parity; run the respective integration/extension-host checks as well.
