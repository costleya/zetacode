## Commands and editor interactions

Keep the command IDs stable. User-visible titles may be newly written.

| Command ID               | Current command title                 | Purpose                                                                                           |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `sweep.triggerNextEdit`  | NESweep: Trigger Next Edit Suggestion | Asks VS Code to trigger inline suggestion computation.                                            |
| `sweep.toggleEnabled`    | NESweep: Toggle Enabled               | Flips the effective enabled setting and hides a visible suggestion when disabling.                |
| `sweep.showMenu`         | NESweep: Show Menu                    | Opens the status menu.                                                                            |
| `sweep.acceptJumpEdit`   | NESweep: Accept Jump Edit             | Accepts the currently displayed non-inline jump edit.                                             |
| `sweep.acceptInlineEdit` | NESweep: Accept Inline Edit           | Forwards the accepted inline-suggestion payload to the provider for acceptance tracking/handling. |
| `sweep.dismissJumpEdit`  | NESweep: Dismiss Jump Edit            | Clears the currently displayed jump edit.                                                         |

Keybinding behavior:

- Tab accepts a jump edit when the editor has focus, no text selection exists, and neither an inline suggestion nor the normal suggestion widget is showing.
- Alt+Tab accepts a jump edit when the editor has focus and there is no selection. Linux also has Alt+L as the alternate binding.
- Escape dismisses a jump edit while one is active.
- When a normal inline suggestion and suggestion widget are both visible, Alt+Tab commits the inline suggestion; Linux also has Alt+L. Escape hides an inline suggestion when the widget is not visible and no jump edit is active.
- Preserve the `sweep.hasJumpEdit` context state that controls those bindings.

The status item is right-aligned and opens `sweep.showMenu`. It shows an idle icon normally and cycles through four loading frames at 150 ms intervals while a request is processing. Its tooltip conveys enabled/disabled and snoozed/not-snoozed state; disabled or snoozed state receives the warning background.

The menu provides these actions:

1. Toggle autocomplete.
2. Snooze for 15 minutes, 30 minutes, one hour, or four hours; persist the chosen global expiry, then hide an existing inline suggestion.
3. Resume by clearing the expiry.
4. Check local models by retrying managed-server readiness and pinging the local client. Report readiness on success.
5. When an editor has an applicable language-rules path, open or create that file and report its character count/overflow state.

The rules-file diagnostic updates as matching files open/change and when the cap setting changes. It clears when the document closes or drops below the cap. The menu's edit-instructions item is available only when the active editor is inside a workspace and its language has a known comment style; selecting it creates the corresponding file if needed and opens it. Rules content is included in completion context when nonempty and is wrapped as language comments; the file is workspace-local and no rule file is created automatically.

## Extension lifecycle

At activation, initialize the output channel and telemetry/tracking services; create the managed local model service, completion client wrapper, inline-edit provider, jump-edit manager, status item, and rules diagnostics. Register the commands and text/editor/theme listeners. Track edits in the active document, route saves to the API client, and forget tracked data when files are deleted. Begin model preparation asynchronously so activation remains responsive. On deactivation, flush tracking state, dispose editor providers/decorations, shut down telemetry, then dispose the log channel.

## Logging and local-model service

- Create one VS Code output channel named for the product; support trace, debug, info, warning, and error levels through VS Code’s log-level controls.
- Convert arbitrary log arguments to readable text: keep strings, prefer an Error stack with message fallback, otherwise attempt JSON and fall back to ordinary string conversion. Separate multiple arguments with spaces.
- Start the managed local model service during extension activation, but do not block activation on model preparation. Completion requests and manual health checks share the readiness gate.
- Use the managed socket and gRPC completion client; do not add public URL/port settings. Lazily create and cache the client, ping only after readiness, and dispose the client on shutdown.
- A readiness failure returns an unsuccessful manual check; managed setup reports its own failure and offers its output channel. A failed ping can show the local-model warning. Three consecutive primary completion failures trigger that warning path; the counter resets at the threshold, and repeated warning displays are suppressed for 60 seconds. A successful primary completion clears both the counter and suppression state. Continuation-model failures do not count against the primary server warning threshold.
- Keep the status bar’s processing signal connected to API in-flight work, not merely to server readiness.
